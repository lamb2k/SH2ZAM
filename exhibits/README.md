# SH2ZAM interactive math lab

The lab compares the CPU work required to transform the same meshes **without
SH2ZAM and with SH2ZAM, compiled for SH-2 and executed in the same instruction
model**. The browser displays recorded model results and a live visual precision
check. It does not collect or display browser transform timings.

Choose a scene and mesh detail, then compare a standalone fixed-point C or
software-float baseline with SH2ZAM's prepared batch or optional native MAC.L
batch. The default comparison is **plain fixed-point C → native MAC.L**. The
native kernel is an explicitly selected experimental API, not the default
prepared dispatcher.

| Exhibit | Workload |
|---|---|
| Ring world | Low-poly planet and concentric rings |
| Cube field | Many cubes in one vertex batch |
| Twisted orbit | Continuous torus-knot mesh |

## What the numbers mean

The headline cards show modeled cycles per complete batch, cycles per vertex,
the relative cost, and the percentage of transform CPU work saved. A negative
saving remains visible as an increase in cost. Scene and detail controls select
the matching recorded workload; animation does not generate new measurements.
Each recorded result is a median across 21 poses. It is not a measurement of the
current browser frame.

| Path | Purpose |
|---|---|
| Plain fixed-point C | Independent bounded Q16.16 affine transform without SH2ZAM arithmetic calls; the baseline for code that already uses fixed point. |
| Software float | Ordinary C float32 affine transform, compiled to SH-2 software-float helpers; the baseline for porting floating-point code. |
| SH2ZAM prepared | The library's prepared batch API with cached immutable mesh bounds and per-matrix qualification. |
| SH2ZAM native MAC.L | Optional prepared batch using fused SH-2 accumulation when its proof and SR.S guard permit it. |
| SH2ZAM safe / native DMULS.L | Additional library paths retained in the detailed model evidence. The safe path is already SH2ZAM, not a no-library baseline. |

Both C baselines and the library are built with the same SH-2 toolchain and
optimization settings. The fixed-point baseline reuses matrix values, unrolls the
three rows, accumulates in 64 bits, and floors each output once. It receives the
same bounded coordinates and matrices and is checked against the same independent
oracle.

Measured paths include their range wrapper and every output store. Independent
plain-fixed qualification and SH2ZAM plan qualification are included once per
whole batch in their respective totals. The common measurement boundary excludes
one-time immutable input preparation, matrix generation, float input conversion,
rendering, and precision checks. Setup is added per pose before taking a median.

The recorded model executes the actual big-endian SH-2 ELF, including libgcc
software-float routines and native multiplication instructions, through pinned,
unmodified Yabause opcode handlers. The UI uses a validated summary generated by
`compile-model-results.cjs`; raw samples and complete provenance remain in the
[SH-2 model evidence](../saturn/benchmarks/sh2-model/README.md).

**These are instruction-model results, not physical Saturn timings.** The model
uses flat RAM and excludes cache, bus wait states, pipeline and multiplier
contention, DMA, interrupts, peripherals, and second-CPU activity. The lab does
not turn its cycle counter into Saturn milliseconds or game FPS. Console captures
remain separate and unmeasured until the
[physical-console benchmark](../saturn/benchmarks/README.md) produces evidence.

## Math library improvements

The second results section compares **SH2ZAM at `10786b6` with optimized
SH2ZAM**, separately from the independent transform adoption baseline. Select
one of 48 existing APIs to see bounded, tiny and full-range inputs together.
The initial operation is 3D vector normalization.

Each cell reports the median of seven deterministic 32-call batches, divided
by 32 to give modeled cycles per call. Both versions use the same input bytes,
range wrapper and result writes. Fixture generation and output comparison sit
outside the measured range. Every output must match exactly, and native stack,
callee-saved register and SR.S checks must pass. Regressions and unchanged
results are represented explicitly; no aggregate across unrelated APIs is
presented as a universal speedup.

`compile-math-results.cjs` applies the strict math evidence validator before
creating `math-results.js`. The page rejects absent or invalid evidence rather
than substituting measurements. Raw samples, frozen-source checksums, compiled
ELF identity and model limitations are retained in the export. See
[the suite and input profiles](../saturn/benchmarks/math-model/README.md) and
[the implementation/results guide](../saturn/MATH_OPTIMIZATIONS.md).

## Live visuals and precision

The two images run together: a float32 reference and SH2ZAM output. Both receive
the same quantized vertices and matrix coefficients. The browser runs the actual
C implementations as WebAssembly with `SH2Z_FORCE_PORTABLE=1` to visualize their
outputs; it does not emulate native MAC.L in the canvas renderer.

The browser's optimized visual path can select coordinate reuse for sufficiently
repetitive immutable meshes, or use the prepared scalar path. That visual choice
does not change the selected native benchmark or its recorded results. The
[coordinate-reuse contract](../saturn/COORDINATE_REUSE.md) describes those APIs.

Every displayed pose checks the safe and optimized fixed outputs bit for bit and
checks their error against float. The target model separately compares fixed
outputs with an independent 128-bit oracle. The float error excludes common
matrix and trigonometry quantization. Camera, triangle colors, lighting and Canvas
projection are shared; the displayed screen offset is a per-vertex CSS-pixel
displacement, not a Saturn rasterizer measurement.

Mesh detail is the only slider and changes the workload for both images and the
selected model record. Pause/play affects animation only. Reduced-motion
preferences start paused, and hidden tabs stop advancing the simulation clock.
Model results, source links, selection controls, and model export remain usable
when WebAssembly is unavailable; only the live visual check requires it.

## Evidence export

**Export model results** downloads the selected scene/detail record, the chosen
baseline and library kernel, the derived comparison, and the recorded model
provenance. The selection envelope is `sh2zam-model-selection-v1` and identifies
`isolated-sh2-interpreter` execution. It includes the source commit, ELF and
interpreter identities, fixture hash, guard results, and model limitations.

When the math capture is present, the same export also includes `mathLibrary`:
the selected family/operation plus the complete validated 144-record dataset
and every raw math sample. The math results and export work independently of
WebAssembly and animation.

The export contains model cycles, not browser wall time. It does not imply that
changing the animation pose reruns the model. Full raw per-pose samples can be
obtained from the evidence link.

## Run and build

The **Interactive math lab** GitHub Actions workflow produces a ready-to-run
`sh2zam-interactive-lab` artifact. Extract it and open `index.html`, or serve it
with `python3 -m http.server --directory exhibits 8000`. All scripts, the compiled
visual module and artwork are local; no CDN, account, or analytics is used.

To build from source, install Clang with the WebAssembly target, LLD, Python 3 and
Node.js, then run from the repository root:

```sh
bash exhibits/build.sh
node exhibits/test-math.cjs
node saturn/benchmarks/test-model-results.cjs
node saturn/benchmarks/math-model/validate.cjs
python3 -m http.server --directory exhibits 8000
```

Open `http://localhost:8000`. The build validates and packages the committed model
evidence; it does not rerun the native CPU model or substitute browser timings.
A self-contained base64 module supports the downloaded site over `file://` in
browsers that allow local scripts. Generated assets are ignored by Git and built
from source in CI.

## Verification

`test-math.cjs` checks WebAssembly buffer isolation and bounds, identity,
safe/optimized equality, prepared fallback selection, and float precision across
all 315 shared mesh/pose combinations. Host tests and the native model cover their
own arithmetic and dispatch contracts; host fallbacks do not execute SH-2 assembly.

`test-browser.py` verifies all 15 model workloads, baseline and kernel selection,
model-derived savings, honest slower results, evidence export, and separation of
model costs from animation. It also covers exact visual checks, the single-slider
layout, pause/play, mobile layout, reduced motion, offline loading, and model
availability when WebAssembly fails. It does not collect browser benchmarks.

The math checks exercise all 48 operation selectors, all three profiles,
zero-change and cost-increase formatting, combined evidence export, keyboard
navigation and mobile layout. Missing, incomplete or invalid math evidence
must suppress its figures while leaving the vertex comparison usable.

Run it with Playwright and Chromium installed:

```sh
python3 exhibits/test-browser.py
```

Set `CHROMIUM_PATH` to an existing compatible Chromium executable when needed.
The model-data validator independently recomputes inclusive medians from raw
samples and rejects invalid output checks, provenance, fixtures, and dispatch
guards. The broader library oracle suites cover full-range fallback, matrix
snapshots, aliasing, range boundaries and workspace contracts.

## GitHub Pages

The workflow deploys the tested static site from `main` using GitHub Pages. If
Pages is not configured or the workflow cannot enable it, the tested downloadable
artifact remains available. A repository administrator can select **Settings →
Pages → Source: GitHub Actions**, then rerun the workflow. Deployment success is
required before announcing a published update.
